# observability-lab — context for whoever picks this up

Read this first. It is written so a person or a coding agent can be useful here within a minute,
without reading the rest of the repo.

## What this is

A hands-on observability lab built on a K3s cluster. It is **not** a tutorial that installs tools in
order. Every phase starts from **one concrete pain** of a fictional company and ends when that pain is
demonstrably gone.

**Vantia is fictional.** The company, its customers and its support tickets are invented. The
scenario is deliberately generic because it is the scenario of many real companies. Nothing here is a
real client case study.

## The scenario

Vantia is a B2B SaaS with an AI support assistant running on Kubernetes. A customer asks a question,
the assistant searches a knowledge base and answers.

Three services, with a queue between them:

```
loadgen → vantia-gateway → [q:retrieval] → vantia-retrieval → [q:llm] → vantia-llm-worker
                                    (Redis)                      (Redis)
```

**The path is real, the work is simulated.** No model is ever called: latency and token counts come
from realistic distributions. That is deliberate — a real HTTP-then-queue path is what makes
correlation genuinely hard, and simulating lets anomalies be injected on demand instead of waited for.

Four injectable scenarios: `normal`, `slow_retrieval`, `token_spike`, `tenant_error`.

## The phases — one pain each

| # | The pain | What closes it | State |
|---|---|---|---|
| 1 | "A customer complains about an answer from Tuesday and we cannot reconstruct what happened" | Fluent Bit → OpenSearch, correlation by `request_id`, index lifecycle | **done** |
| 2 | "Sometimes it answers in 3 seconds and sometimes in 40, and we cannot say where they go" | Grafana + OpenTelemetry Collector + Tempo | **done** |
| 3 | "The model bill tripled and nobody knows what raised it" | Tokens and cost as span attributes, per tenant and stage | not started |
| 4 | "Engineering will not leave Grafana, and retention costs do not scale" | Loki as a second output of the same pipeline | not started |
| 5 | "I have the alert. Now where do I look?" | trace ↔ logs ↔ metrics correlation, and alerts that open in the right place | not started |

**The thread across all of them**: the `request_id` that phase 1 propagates by hand and has to be
searched for becomes, in phase 3, an OpenTelemetry `trace_id` that propagates itself and draws itself.

## Current state

**Phase 1 is complete.** The application is running and its logs are structured, the log store
exists, and **nothing connects the two yet** — that is the remaining work in phase 1.

- Namespaces: `vantia` (the app under observation), `observability` (the system that observes it).
- Image: `sauay/vantia:0.1.0` — one image, three roles selected by `VANTIA_ROLE`.
- Gateway exposed on NodePort `30830`.
- OpenSearch 3.8.0, single node, green, **empty**. Redeploy with `./scripts/deploy-opensearch.sh`.
- OpenSearch Dashboards 3.8.0 on NodePort `30832`, **LAN only, never through a tunnel**. Log in as
  `admin` with the password in the `opensearch-admin` secret.
- Only two accounts exist in OpenSearch, `admin` and `kibanaserver`, both with generated passwords in
  secrets. The five demo accounts that ship with published passwords were removed.

- Index template `logs-k8s-*` with explicit field types, write alias `logs-k8s`, and an ISM policy
  (hot 1h → warm 6h → delete 24h; production would be 7d / 90d / 1y). Rebuild with
  `./scripts/bootstrap-index.sh`.

- Fluent Bit as a DaemonSet on all three nodes, tailing only `*_vantia_*.log`, writing to the
  `logs-k8s` alias with a `fluentbit` account that can write and not read.
- Dashboard `Vantia — support assistant`, versioned as `opensearch/vantia-dashboard.ndjson`.

The pain of phase 1 is closed and measured: one search rebuilds a whole conversation, and it survives
restarting every service (`kubectl logs` 3 of 3 → 0 of 3; OpenSearch 3 of 3 → 3 of 3).

**Phase 2 is under way.** Grafana (NodePort 30833, two datasources as code), Tempo (single binary,
24h retention) and the OTel Collector are deployed, and Vantia image `0.2.0` is instrumented: one
request produces three correctly nested spans carrying tenant, tokens and cost. Context travels
inside the queue message with `inject`/`extract`, the standard doing what phase 1 did by hand.
Correlation is demonstrated both ways: a log line's `trace_id` returns the three spans, and a span's
trace id returns the three log lines. `scripts/why-slow.sh` is the demo as a command — it finds the
slowest request, prints its logs, and draws the waterfall. Dashboard
`Vantia — one request, both signals` is generated by `grafana/make-dashboard.py`.

Next is phase 3: tokens and cost per request, attributable to tenant and stage. The fields are
already on the spans.

The original plan was: **Grafana + OpenTelemetry Collector + Tempo.** Traces were moved ahead of Loki —
Loki is the smallest remaining gap, tracing is the largest, the cost-and-tokens phase depends on
traces, and Tempo has no UI of its own so Grafana is needed either way.

Known debt: the TLS certificates are still the image's self-signed demo ones. Fine while nothing
leaves the cluster; replace with a real PKI before it does.

## Try it in thirty seconds

```bash
./scripts/ask.sh acme                  # sends a question, returns a request_id
./scripts/trace.sh <request_id>        # hunts for it across every pod
./scripts/prove-log-loss.sh            # shows a line disappearing from kubectl logs on restart
./scripts/find.sh <request_id>         # the same hunt, asking one place instead of every pod
```

Or without the scripts:

```bash
curl -sS -X POST http://<node-ip>:30830/ask \
  -H 'content-type: application/json' \
  -d '{"tenant":"acme","question":"why was my invoice charged twice","scenario":"normal"}'
```

Valid tenants: `acme`, `globex`, `initech`, `umbrella`, `soylent`. Anything else returns 404 and logs
a rejection.

Without a NodePort: `kubectl -n vantia port-forward svc/vantia-gateway 8080:8080`.

## The log line, which is the whole point of phase 1

```json
{"ts":"...","service":"llm-worker","request_id":"1a1949362f3d","tenant":"acme",
 "stage":"generate","status":"ok","model":"large","tokens_in":1955,"tokens_out":150,
 "cost_usd":0.001957,"latency_ms":2174.67,"total_ms":2255.04}
```

`latency_ms` is what this stage took. `total_ms` is what the customer waited. **The gap between them
is queue time**, and keeping them as separate fields is what makes it visible at all.

`tokens_in`, `tokens_out`, `cost_usd` and `model` are useless in phase 1. They are written now
because phase 4 needs them, and because adding a field later leaves you with no history.

## Rules to follow when changing anything here

1. **Every pod must set `priorityClassName: lab-low`.** This is enforced by a
   ValidatingAdmissionPolicy on namespaces labelled `tier: lab`; a pod without it is rejected. The
   lab may share a node with other workloads, and it must be the first thing evicted under memory
   pressure, never the last.
2. **Every PVC must set `storageClassName` explicitly.** Never assume the cluster default.
3. **Pin chart versions.** `helm upgrade` without `--version` resolves to whatever is newest in the
   repository, which is not a scoped operation.
4. **Kubernetes YAML in block style.** No `matchLabels: { app: x }`. Manifests should look like the
   ones everyone else reads and like what `kubectl get -o yaml` returns. Flow style is reserved for
   the two cases with no alternative: empty collections (`resources: {}`, `tolerations: []`) and Helm
   `values.yaml`, where it is the convention.
5. **No comments in code.** Names and structure carry the meaning.
6. **Everything public is in English.**
7. **Changing security config is two steps.** The chart mounts `internal_users.yml`; it never
   applies it. The live configuration lives in the `.opendistro_security` index, so
   `apply-security-config.sh` has to push it with `securityadmin.sh` and the admin certificate.
8. **System indices are out of reach of the permission model.** No role grants access to them, not
   even admin's; only the `kirk` admin certificate does. That is why replica fixes on plugin indices
   run inside the OpenSearch pod instead of from the bootstrap Job.
9. **`subPath` mounts never refresh.** The chart mounts `internal_users.yml` that way, so changing
   the Secret is not enough: the pod has to restart before the new file is even visible, and
   `securityadmin` will apply the stale one and report success.
10. **A phase is not finished when the pods are green.** It is finished when the pain is demonstrably
   closed and the write-up exists.

## What not to assume

- The load generator is not a benchmark. It produces a realistic *mix*, not a realistic *volume*.
- Redis has no persistence on purpose: it is a queue for a demo, not a store.
- The three services keep no state and store no answers. There is nothing to query afterwards except
  the logs — which is the point.
